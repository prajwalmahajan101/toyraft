## Goals

Give ToyRaft a **real-network** partition test — one that exercises the failure
mode the Phase-11 loopback chaos cannot reach — behind a build tag, using Linux
network namespaces for automatic teardown:

> Add real-network partition tests behind a build tag, using Linux netns for
> automatic teardown; partition two nodes with `iptables -j DROP`, assert
> recovery, and prove the namespace is gone after `t.Cleanup`. Retire risk D-1
> (loopback masking that inproc and process-kill cannot detect).

## Decisions made (non-ADR)

- **N=3** — the minimum clean odd majority for "partition two, third holds
  quorum" (RESEARCH Open-Q4).
- **No race detector on the `netns` job** — the test orchestrates external
  daemons; `-race` only instruments the barely-concurrent test process, adding
  cost with no signal (RESEARCH Open-Q3).
- **Deadlines widened to 8s** from process-kill's 1s/2s — a real L3 `DROP`
  blocks TCP until the ~150ms `SendTimeout` then retries, so recovery over a
  veth hop is slower than loopback (RESEARCH Pitfall 7).
- **Per-run randomized ns/bridge/subnet names** from the pid, for idempotency
  against a crashed prior run (RESEARCH Pitfall 4); assumes one netns test per
  `go test` process.
- **Recorder dropped** — no Phase-12 history for this path (SC1 is
  partition + recovery + namespace-absent teardown, not a Porcupine artifact).
- **SC3 read as "dedicated job = the linux-amd64 entry."** RESEARCH flagged the
  tension between a dedicated `ubuntu-latest` job (Option A) and the literal
  "matrix entry" wording; resolved to Option A (one linux-amd64 runner, never
  macOS) and recorded in the ci.yml comment, ADR-0020, and here.

## Risks retired

- **D-1 (loopback masking).** Retired. Phase-11's inproc + process-kill chaos
  run over `127.0.0.1`, where the kernel loopback path cannot exhibit a real
  partition — a `DROP` there is not an unreachable peer. Phase 13 gives each
  `toyraftd` its own network namespace + veth + non-loopback IP on a shared
  bridge and severs a single link with per-namespace `iptables -j DROP`, so a
  real L3 `DROP` across distinct addresses now exercises the
  dial/timeout/reconnect path that loopback cannot. `TestNetnsPartition` asserts
  surviving-majority commit through the partition and full re-convergence after
  heal (positive oracle over the `/status` commit_index seam).

## What surprised us

- **Option A's honest cost was a branch-protection change, not a test change.**
  Reusing the `test` job (as Phase 11/12 did) is free; a dedicated `netns` job
  is the cleaner expression of "linux-amd64 entry only" but adds the 8th
  required check — which ADR-0002 explicitly says obliges an ADR entry *and* a
  branch-protection update. The narrow `required_status_checks` endpoint made
  the update safe (it touches only the contexts array), and a before/after diff
  proved the other seven contexts and four toggles survived.
- **`gh api` will require a context that has never been observed.** `netns` was
  added to the required set before its first CI run; the first phase-PR run then
  satisfies it. No chicken-and-egg wait.
- **The verify greps false-positive on prose describing an absence.** The
  terminal-failure comment and the "no race detector" comment originally
  contained the literal `if:` / `continue-on-error` / `-race` tokens the SC3
  gate greps for — the same class of reword the 13-01/13-02 executors hit. The
  step itself is a plain `run:` with zero modifiers; only the comment prose was
  reworded to carry none of the forbidden tokens.

## Post-open CI fix — bridge had no host IP (root-ns could not observe the cluster)

The first real `netns` CI run (PR #18, `ubuntu-latest`, under root — the phase's
whole point is that this path only executes in CI/root) **failed**:

```
toyraftd up  id=n0 peer_addr=10.116.0.10:7001 client_addr=10.116.0.10:9001
--- FAIL: TestNetnsPartition (7.48s)
    netns_test.go:74: no initial leader within boot deadline (seed=13)
```

**Root cause (see `.code_assist/.debug/DEBUG.md`):** `newHarness` built the bridge
(`ip link add … type bridge` + `set up`) but **never assigned it a host IP** in the
node subnet. The test process polls each node's `/status` from the **root
namespace**, so it needs a connected route to `10.<octet>.0.0/24` — which only exists
once the bridge carries an address there. Without it the cluster elected a leader
**fine internally** (ns↔ns over the bridge, same subnet), but the test was **blind**
to it: every root-ns poll to `10.x.0.1i:9001` failed → `findLeader` timed out.

The tell: the in-harness `ip netns exec <ns0> ping <ip1>` sanity check **passed**
(it runs *inside* a namespace, exercising the healthy ns↔ns plane) while the root-ns
observation path was broken. RESEARCH's topology diagram had labelled the bridge
gateway IP `10.0.0.254/24` **"optional"** — it is in fact **required** for a harness
that observes from the root ns. Hypotheses H1 (Docker `FORWARD DROP` /
`bridge-nf-call-iptables`) and H2 (150ms transport `SendTimeout`) were both refuted
by the passing ns-ping.

**Fix (`test/chaos/netns/harness.go`):**
1. Assign the bridge a host IP: `sudo ip addr add 10.<octet>.0.254/24 dev <bridge>`
   (new `gwIP` field) → the root ns gets a connected route to the node subnet.
2. Add a **root-ns reachability guard** right after the ns↔ns ping:
   `sudo ping -c1 -W1 <ip0>` from the root ns — a regression tripwire that fails
   loudly at setup ("root cannot reach the node subnet") instead of resurfacing as a
   downstream "no initial leader". This is the exact path the missing IP broke.

Teardown is unchanged — `ip link del <bridge>` removes the address with the bridge.
`go build -tags=netns` / `go vet -tags=netns` stay green; the test still SKIPs
without root. Verification of the fix is the CI `netns` job going green on the fix
commit (the only place the full partition run executes). **Lesson:** a chaos harness
that observes the SUT from a different namespace than the SUT runs in must wire the
observation path explicitly — and prove it with its own reachability check, not just
the SUT-internal one.

**Second failure (bug #2) — partial partition flapped leadership.** With bug #1
fixed, the next CI run got a leader and committed the first post-partition writes,
then failed:

```
--- FAIL: TestNetnsPartition (4.04s)
    netns_test.go:117: post-partition set p2: PUT .../kv/p2: context deadline exceeded
```

`p0`/`p1` committed; `p2` timed out. Root cause: the test cut only the `n0<->n1`
**link**, but n2 still reached both. `pkg/raft` has **no PreVote and no check-quorum
step-down**, so the two split nodes alternately won n2's vote → **leadership flapped**
and terms inflated; a write that landed on a momentary leader blocked in `Propose`
when that leader lost quorum on the next flap → the 2s client timeout. A single-link
cut in a 3-node cluster is a *partial partition*, not a clean majority split. RESEARCH
Open-Q4's "cut n0↔n1, n2 bridges quorum" shape was wrong for a no-PreVote cluster.

Fix: replace the single-link cut with **full isolation of one follower**
(`isolate(v)`/`rejoin(v)` in the harness — cut node v from *every* peer, reusing the
per-link primitive). Isolating one node leaves the other two a **stable** connected
majority (the isolated node's election packets are all dropped, so it never disrupts
the majority while the partition holds); the current leader keeps committing. Writes
now go through `commitKV(k,v,deadline)`, which re-finds the leader and retries — this
absorbs the ONE disruptive re-election a no-PreVote node forces on **rejoin** (its
inflated term makes the leader step down once). **Lesson:** for an N=3 partition test
against a Raft without PreVote/check-quorum, isolate a *minority* cleanly — don't cut
a single link and expect a stable survivor; and drive writes through a
leader-re-finding helper so a disruptive rejoin doesn't flake the oracle.
